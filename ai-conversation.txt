  4. Decisions I made that we did not discuss

  1. HOLD comes before rules 1 and 2. An international order with an unknown SKU
     goes to HOLD, not PARTNER. This follows your reasoning that the partner
     can't ship an unknown product either.
  2. Missing or blank country goes to HOLD ("missing country"). I didn't want to
     guess either US or international.
  3. An order with no items goes to HOLD ("no items"). Otherwise every warehouse
     would qualify for it.
  4. Fixes that get a note: padded ZIPs, trimmed ZIPs, SKU case or whitespace
     changes, country case or whitespace changes, and merged or ignored edits.
  5. Things that get no note:
     - ZIP+4 (that's a valid format, not a fix).
     - A 5-digit ZIP stored as a number (nothing changes about its value).
     - Bundle expansion (that's a catalog lookup, not a fix).
  6. Edit window rules:
     - The window is 0 to 30 minutes after creation, with exactly 30 included.
     - An edit outside the window, or one dated before its order's creation, is
       ignored and noted on that order's line.
     - An edit for an order that doesn't exist only prints a warning to stderr,
       so it never appears in routes.txt.
  7. A second order_created with the same order number is ignored, and so is an
     unknown event type, each with a warning on stderr. The first order_created
     is the one kept.
  8. No @types/node. I wrote a small declarations file, types/node-shim.d.ts, so
     typescript stays the only devDependency. The catch: if the code starts
     using more of Node, that file has to grow.
  9. TypeScript 7.0.2 (latest, the native rewrite), pinned to that exact
     version.
  10. What "in zones" means for rule 2: the prefix is in the zone table of at
      least one warehouse in warehouses.json, enabled or not. A warehouse with
      no zone for the prefix can't take the order.
  11. A SKU missing from a warehouse's inventory counts as 0 stock and 0 days of
      cover.
  12. The priority list (rule 6): a warehouse not in it sorts last.
  13. --off options:
      - It accepts --off WH-NV, --off WH-NV,WH-GA and --off=WH-NV, can be
        repeated, and ignores case.
      - An unknown warehouse code is an error.
      - The "routes.txt not written" message and all warnings go to stderr, so

  2. Edits to an order with an invalid created time are not merged, because the
     30-minute window can't be measured. The line gets the note "edit ignored,
     created time unknown".
  3. Invalid quantity in an edit outside the window. It doesn't hold the order,
     because that edit is ignored anyway; the note shows it, e.g. -3 B.
  4. Lines with an invalid quantity are left out of the items, as well as
     holding the order, so they can never touch stock even by mistake.
  5. Several HOLD reasons are all shown, joined with ; , in this order: created
     time, quantity, unknown SKU.
  6. A SKU that isn't a string counts as an unknown SKU.
  7. How strict the type guards are:

       or lines doesn't drop the order; it ends up on HOLD or PARTNER for the
       usual reasons.

       the same as any unrecognized event.

  Add --avoid to route away from a slow warehouse

  Part B asks whether to stop routing to WH-GA while it is behind on

  6. Decisions I made on my own

  1. Ranking rules now receive the full candidate set (a new third parameter on
     compare). This was needed for correctness, as explained in section 1.
  2. Override rules carry a note, and the note is decided by a counterfactual. I
     pick again without the rule, and add the note only if the warehouse
     differs. Tie notes ignore override rules. "Primary" is now the first rule
     that isn't an override, so zone deciding still adds no tie note.
  3. The avoid rule sits first, before zone.
  4. "Another warehouse" means any other candidate that is enabled, has a zone
     for the ZIP prefix and has stock for the whole order, including one in a
     closer zone.
  5. --avoid takes exactly one warehouse; two or more is an error. --avoid and
     --off on the same code is allowed; the avoid rule then has no effect.
  6. Note text and order: the tie note, then avoided WH-GA at zone N, then the
     input-fix notes.
  7. #2038 loses its tie: cover note in run c. The avoid rule decided it before
     cover could, and it picked the same warehouse, so there's no avoid note

  8. How I applied Priya's numbers:

  # Order router

  A skills test. Part A routes each order of a fictional supplement shop to one
  warehouse. Part B is two decisions based on its results.

  ## 1. The problem

  Each order goes to one warehouse: the closest one that can ship the whole
  order. The input is in `data/`: the day's order events, the warehouses with
  stock and daily sales, the shipping zone from each warehouse to each ZIP
  prefix (1 is closest), and the catalog.

  | Rule | In plain words |
  |---|---|
  | 1 | Outside the US: PARTNER, the international partner warehouse. |
  | 2 | No ZIP, or a ZIP prefix (first 3 digits) with no zone: PARTNER. |
  | 3 | A warehouse can take the order only if it is enabled and has stock for
  every item. No splits. |
  | 4 | The lowest zone wins. |
  | 5 | Tie: the most days of cover wins (stock ÷ daily sales, smallest over the
  order's products). |
  | 6 | Still tied: WH-NJ, WH-GA, WH-NV, WH-TX. |
  | 7 | No warehouse can take it: PARTNER. |

  Orders are routed in creation order, and each one reserves its stock.
  Customers can add items for 30 minutes, so each order is routed once, with its
  edits.

  ## 2. How to run

  Node `^22.18.0 || >=23.6.0` (`.nvmrc` says 24). Node runs the `.ts` files
  directly.

  ```sh
  npm install         # dev dependencies only, for type checking
  npm start           # writes routes.txt
  npm test
  npm run typecheck
  ```

  | Flag | Effect |
  |---|---|
  | `--off WH-NV` | Turns warehouses off. Takes a list: `--off WH-GA,WH-NV`. |
  | `--avoid WH-GA` | Routes away from one warehouse when another one that can
  take the order is within one zone of it. |

  Example: `npm start -- --off WH-NV --avoid WH-GA`. A run with a flag prints
  only. `routes.txt` always comes from the files as given.

  ## 3. The output

  ```
  #2033  WH-NJ    zone 3 (ZIP 2134 read as 02134)
  #2034  WH-GA    zone 5 (tie: cover)
  #2037  PARTNER  outside US (country CA)
  ```

  | Destination | Reasons |
  |---|---|
  | A warehouse | `zone N` |
  | PARTNER | `outside US (country X)`, `no ZIP`, `invalid ZIP X`, `ZIP prefix X
  not in zones`, `no warehouse can take the whole order` |
  | HOLD (a person decides) | `unknown SKU X`, `invalid quantity`, `invalid
  created time`, `missing country`, `no items` |

  The notes in parentheses show what a person should see: input fixes (`SKU
  nw-mag-90 read as NW-MAG-90`, `edit merged: +1 NW-MULTI-30`), tie-breaks
  (`tie: cover`, `tie: priority`), and the avoid rule (`avoided WH-GA at zone
  7`, only when it changed the warehouse).

  ## 4. Messy data

  Each problem has a general rule. No rule uses an order number.

  | Problem | Example | Rule |
  |---|---|---|
  | ZIP lost its leading zero | `2134` | Digits only and fewer than 5: pad with
  zeros. |
  | ZIP+4 | `07030-1834` | Use the first 3 digits. |
  | Non-US postal code | `M5V 2T6` | Invalid ZIP. |
  | `CA` is Canada as a country, California as a state | | Only `country`
  decides rule 1. |
  | Lowercase SKU | `nw-mag-90` | Trim and uppercase. |
  | Empty ZIP, or a prefix with no zone (Hawaii) | `""`, `968` | PARTNER (rule
  2). |
  | Bundle SKU that no warehouse stocks | `NW-BNDL-ESS` | Expand into its
  products. |
  | Order edited later | `order_edited` | Merge within 30 minutes, else ignore
  with a note. |
  | A `_note` key among the warehouses in `zones.json` | | Look up zones by
  warehouse code. |
  | Daily sales of 0 | WH-TX | Infinite cover, not a division by zero. |

  ## 5. My readings of the rules

  | Choice | Reason |
  |---|---|
  | An edited order keeps its creation place in the queue. | Every order waits
  the same 30 minutes, so the sequence is the same. |
  | Cover uses stock before this order is reserved. | The literal reading. The
  other reading changes no winner today. |
  | Unknown SKU: HOLD, not PARTNER. | The partner can't ship a product nobody
  knows. Rule 7 is about stock. |
  | Invalid quantity (0, negative, not whole): HOLD. | A negative quantity would
  add stock and silently break later orders. |
  | Missing or invalid created time: HOLD. | The queue decides who gets stock,
  and this order has no place in it. |
  | Pad short ZIPs, numbers and strings alike. | `"2134"` lost its zero the same
  way `2134` did. |

  ## 6. Design

  | File | Job |
  |---|---|
  | `src/normalize.ts` | Raw events to clean orders: ZIP, SKU, bundles, edits,
  hold reasons, notes. |
  | `src/router.ts` | Rules 1 to 7, stock reservation, the ranking list. |
  | `src/pipeline.ts` | The whole run, from parsed input to text. |
  | `src/load.ts`, `src/main.ts` | Read `data/`; print and write `routes.txt`. |
  | `src/cli.ts`, `src/format.ts`, `src/types.ts` | Flags, output lines, types.
  |
  | `test/` | Unit tests, and an end-to-end test against
  `test/fixtures/expected-routes.txt`. |

  Normalizing and routing are pure functions. Only `load.ts` (reading) and
  `main.ts` (writing) touch files. Rules 4 to 6 are an ordered list of
  comparators (zone, cover, priority). That list is the one place where routing
  policy changes: `--avoid` adds a rule in front of it.

  Left out:

  - No linter. Strict TypeScript and the tests cover the serious problems in
  eight small files. A linter is the first thing I would add when a second
  person works on the code.
  - No Docker. There are no runtime dependencies, so Node is the only
  requirement.
